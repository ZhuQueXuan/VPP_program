# 验证方案与可信度判断

## 1. 为什么需要多层验证

本算法既有“完成比例是否能被合理描述”的问题，也有“市场激励等因素的解释是否可信”的问题。二者不能只用一个准确率解决。

因此，验证分为四层：数据、模型、稳定性和业务解释。

## 2. 数据层验证：先确认输入可信

| 检查内容 | 要回答的问题 | 不通过时的处理 |
| --- | --- | --- |
| 任务闭环 | 指令、资源和执行结果是否确实对应同一次任务 | 不进入模型，先补对应关系 |
| 完成比例抽查 | 少量任务的计算是否与业务记录一致 | 修正口径或采用系统已有口径 |
| 单位和方向 | 功率单位、上/下调方向是否统一 | 统一换算和标记规则 |
| 缺失和异常 | 是否存在大面积缺失、重复、明显不合理值 | 标注、剔除或单独解释，不静默填补 |

## 3. 模型层验证：模型是否描述得合理

### 3.1 基础对比

将“只看任务要求的简单模型”与“加入资源状态和资源个体差异的混合效应模型”对比。若加入必要信息后结果明显更稳定、解释更合理，说明模型结构有价值。

### 3.2 预测/拟合检查

若数据允许，可用较早时段建模、较晚时段检查，观察完成比例或成功/失败是否仍能被合理描述。这个检查用于模型可用性，不等同于因果验证。

### 3.3 异常任务检查

分别在“包含全部任务”和“去除明显异常/撤销任务”两种情况下重复估计。若结论完全反转，需要查明是否被少量异常任务主导。

## 4. 机制层验证：因素关系是否稳健

| 检查 | 做法 | 希望看到什么 |
| --- | --- | --- |
| 分时段重复 | 按月份、季节或规则变更前后分别估计 | 主要方向不应无合理原因地频繁反转 |
| 分资源组重复 | 对不同资源组或运营单位分别估计 | 能发现差异，但不应只由单一资源决定 |
| 替代口径 | 更换合理的完成比例计算口径或任务筛选规则 | 结论方向基本一致 |
| 安慰剂检查 | 使用理论上不应影响结果的无关变量进行对照 | 不应得到同样强的“影响” |
| 未观测因素敏感性 | 假设存在一个未记录因素，检查需要多强才会推翻结论 | 明确结论对遗漏信息的脆弱程度 |

因果图和这些检查只能提高可信度，不能在纯观察数据下承诺绝对因果。

## 5. 业务层验证：结果能否说得通

模型结果应与调度、交易、营销或运营人员核对三件事：

1. 激励、任务要求和调用优先级在实际业务中如何设定；
2. 结果中的阈值是否可能对应设备边界、市场规则或用户约束；
3. 特别高/低的资源表现是否有可解释的运行原因。

专家校核不是“为了证明模型正确”，而是发现模型遗漏的业务机制或数据口径问题。

## 6. 可信度表达方式

正式输出不只给“有影响/没影响”，建议按以下方式说明：

| 可信度 | 建议表述 | 条件 |
| --- | --- | --- |
| 高 | 在多个时段、资源组和合理口径下结果方向稳定 | 数据闭环完整、稳健性检查通过、业务解释一致 |
| 中 | 存在较清晰关系，但样本覆盖或部分检查有限 | 明确限制条件后使用 |
| 低/待验证 | 数据缺失、样本集中或结果对口径敏感 | 只作为后续采数和研究线索，不进入正式结论 |

## 7. 与“90%精度要求”的关系

课题要求的“模型精度不低于 90%”应在真实数据和验收口径明确后，针对可调容量/响应能力模型单独评价。第一版驱动因素解耦算法主要验证关系解释的稳定性，不能把两类验证混成一个 90% 指标。

## 8. 数据到位后的最小验证包

第一轮至少输出：

1. 数据闭环与缺失检查表；
2. 完成比例口径的人工抽查记录；
3. 基础模型结果和一个替代口径结果；
4. 至少一次分时段或分资源组重复结果；
5. 一页业务解释与局限性说明。
